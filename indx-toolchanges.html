Tool Change Efficiencies

How a Bondtech INDX tool change went from 10.5 s to 5.8 s. No hardware changes, no firmware flash, and the same safety checks.

Summary

Use at your own riskThese are unofficial changes to Bondtech's macros and Kalico, not anything Bondtech has released or reviewed. They worked on my printer, but that doesn't mean they'll work on yours, and they could damage it. If you use anything from this page, you do so at your own risk.

Most of a tool change was spent standing still. The motion itself was quick, but the macros stopped the toolhead about twenty times per change, and every stop costs a fixed restart delay in Klipper. Bondtech's macros stop the head around each step, which keeps every step easy to reason about and safe. Some of those stops are needed. Many look avoidable: they wait for moves that run in order anyway, or pause in a way that doesn't appear to delay what they were placed for. There may be reasons for some of them that aren't visible from the code. Removing those stops, and letting the latch moves queue behind the head moves instead of stopping around each one, cut the time per change by 45%.

How an INDX tool change works

Two parts of the INDX head matter here:

  • The latch that holds the tool is driven by the stepper configured as the head's extruder, so it moves with extruder moves in millimetres. Kalico's INDX module provides INDX_EXTRUDER_MOVE for this: an extruder move that bypasses the cold-extrusion check and runs at a motor current the macro chooses. The rest of the park and pickup is Bondtech's G-code macros. Every change in this write-up is in one of those two places.
  • The load cell checks every change. A seated tool presses on it with the latch's preload, more than 1000 g, so a proper pickup adds that to the reading and a proper park takes it away.

Bondtech's park and pickup

A change is a park of the current tool followed by a pickup of the next one. The trigger line is a point 5 mm in front of the docks where the head lines up before going in.

Park
  1. Lift Z 1 mm, turn the heater off.
  2. Drive to the trigger line in front of the tool's dock.
  3. Weigh the head with the tool on it (the "seated" reading).
  4. Unlock "dance": nudge the latch, step 0.5–1 mm into the dock, nudge again, then drive fully in and open the latch.
  5. Back out and weigh again. The reading must have changed by at least 425 g, or the tool is still on the head and INDX stops.
Pickup
  1. Drive to the trigger line in front of the new tool's dock.
  2. Weigh the empty head.
  3. Drive into the dock (the latch is already open from the last park).
  4. Close the latch.
  5. Back out, let the load cell settle, weigh again. It must differ from the empty head by at least 680 g, or INDX re-homes and retries once.

Why stops cost so much

Klipper plans moves ahead. While the head is moving, the next few moves are already in a queue, so one move flows into the next without stopping. Two things break that flow:

  • Waiting for the queue to empty. M400 in a macro, or wait_moves() in Python, holds up the next command until every queued move has finished. The head comes to a full stop. The next move can't start straight away either: Klipper schedules it at least 0.25 s in the future (BUFFER_TIME_START) so the host can stay ahead of the motors. That is about a quarter of a second of dead time per stop, plus any decelerating and accelerating the stop forces.
  • Changing a motor driver's current. Writing a new current to the stepper driver is a query to the microcontroller that only returns once the microcontroller's clock reaches the requested time. The host can't plan past it, so the queue drains around it.
A trap: G4 doesn't delay the next command, only the next move G4 P250 inserts a 250 ms pause into the motion timeline and returns immediately. A macro that runs M400, then G4 P250 to let a sensor settle, then reads the sensor, takes the reading before the pause: it runs as soon as the G4 has been queued. The pause then only holds up the moves after the reading. Three of the four settle pauses in the original tool change are placed like this. They appear to have added 250 ms of standing still without delaying the reading they were there for.

How it was measured

A small Python script on the printer's host sends each tool change through Moonraker (Klipper's web API). Meanwhile it samples the toolhead's live position and velocity about four times a second, and logs when each command starts and finishes. Every test is a loop through docks T0 → T1 → T2 → T3 → T0, with the hotend cold (TEMP=0) so heating doesn't blur the timing, followed by M400 so the time covers the whole change. "Still" is any stretch where neither the head nor the latch is moving.

The changes

1. Let latch moves queue (Kalico, Python)

INDX_EXTRUDER_MOVE called wait_moves() both before and after every latch move. It also wrote the motor current before and after each one, even when the current wasn't changing. That is a sensible, safe default for a latch move made on its own. Inside a tool change, though, it surrounded every latch move with up to four stops.

A new WAIT=0 option queues the latch move straight behind the head moves before it, like any other move. Klipper already runs an extruder-only move after a head move in order, so the latch still moves only once the head has arrived. The current is now written only when a move asks for clearly less than the run current. That applies only to the squeeze, which deliberately runs the latch motor at 0.2 A instead of 0.6 A so that it gives way while the tool is pushed into the dock. The squeeze keeps its stops, because a current change can't be queued.

wait = gcmd.get_int("WAIT", 1, minval=0, maxval=1)
...
lower = current < run_current * 0.95   # the readback is quantised, so "equal" isn't exact
...
if wait:
    toolhead.wait_moves()
if lower:
    current_helper.set_current(current, hold, toolhead.get_last_move_time())
try:
    toolhead.manual_move(pos, speed)       # the latch move, cold extrusion allowed
    if wait:
        toolhead.wait_moves()
finally:
    if lower:
        current_helper.set_current(run_current, hold, toolhead.get_last_move_time())

Without WAIT=0 the command behaves exactly as before, so Bondtech's macros are unaffected.

Deploying a Python change needs a full service restartThe Klipper console commands RESTART and FIRMWARE_RESTART reload the config, but Python modules that are already loaded stay loaded. The first round of tests silently ran the old code, and WAIT=0 appeared to do nothing. Restart the Klipper service itself, for example with systemctl restart klipper.

2. Take out stops that don't appear to be needed (macros)

In the park and pickup macros:

  • The heater-off shares the stop at the trigger line instead of having its own stop after the Z lift. The heater therefore stays on about a second longer, through the travel to the dock (see the note on ooze below).
  • The 250 ms G4 pauses after the park and empty-head readings go. As explained above, they don't appear to delay the readings.
  • The M400 between the Z lift and the travel, and between backing out and lowering Z, go. Those moves run in order anyway. The stop before the heater turns back on stays.
Ooze, and where to put the prime towerWith the heater-off moved to the trigger line, the nozzle stays hot for about a second longer on the way to the dock, so a parked tool can ooze slightly more. A prime tower placed between the docks and the printed object takes care of this: after every pickup the head passes the tower on its way back and primes there before printing resumes, which clears any ooze before it reaches the part. That placement also shortens the travel to and from the docks, so it is worth doing anyway. Turning the heater off earlier, right after the Z lift as Bondtech's code does, would need its own stop to wait for the last print moves to finish, so that variant wasn't tested.

Every load cell check reads exactly what it read before. The seated readings on the first runs matched the baseline within a few grams.

3. Tune the speeds and pauses

The open and lock now run at 2400 mm/min. That is a constant in _INDX_CONSTANTS, which INDX's calibration macros also use for their latch moves.

During testing, each change was a switch that could be turned on live with SET_GCODE_VARIABLE, so they could be A/B tested one at a time. Once the results were in, the switches came out and the winning behaviour went straight into the macros, which keeps the diff small. The results below are named after the change each step added.

For a sense of scale: the painted Benchy that started this has 376 tool changes. About 4.7 s saved per change is about 29 minutes off a 3 h 25 min print. A hot change mid-print also waits for the next nozzle to reach temperature, which is a separate cost and not covered here.

In a real print

A two-colour PLA print with 73 tool changes ran with every change clean. Six of them were timed from the last extrusion before the change to the first extrusion after it, on the prime tower: 11.3–15.6 s, 13.4 s on average. About 8 s of that is motion: the cold test's 5.8 s plus the trips to and from the prime tower. The rest, 3.5–7.5 s, is the incoming nozzle heating back to temperature. A docked nozzle cools, and its heater is in the head, so nothing can keep it warm in the dock. A tool used 30 s earlier came back at 127–146 °C and took about 4 s; one idle for two minutes was down to 76–83 °C and took about 6.5 s. The nozzle heats at about 20 °C/s, and the macro resumes at 5 °C under the target.

Starting the heater earlier, as soon as the latch locks, would overlap 1–1.5 s of that, but it would mean heating before the seat check has confirmed a tool is there. The head reads nozzle temperature with an infrared sensor aimed where the nozzle should be, and a badly seated tool could read low and be driven hard. That was judged not worth the risk.

The miss. On one pickup the latch closed, but the tool stayed in its dock. The seat check saw an empty head (−172 g), INDX re-homed X and Y as designed, and the retry picked the tool up. The toolhead trace looked like any other pickup. The difference from Bondtech's code is timing: with the latch moves queued, the lock starts the instant the head arrives in the dock, while the original code stopped there for about 0.3 s first. A 100 ms pause before the lock restores some of that settling time, and nothing has missed in 129 changes since. One miss can't prove the pause fixed it, but the pause costs almost nothing, so it stays.

What didn't help

Prusa's "direct" park order: slower here

Prusa's own INDX firmware (toolchanger_indx.cpp in Prusa-Firmware-Buddy) parks by driving straight into the dock at 100 mm/s, wiggling the latch ±0.27 mm, then opening it. Bondtech's macros step into the dock in 0.5–1 mm increments with a latch nudge at each step. We tested a "direct" option which copied Prusa's order, with Bondtech's latch distances.

It took 7.08 s against 6.03 s for the dance, so it isn't in the final code. In the direct order both the squeeze and the wiggle run at the reduced 0.2 A, and every current change forces a full stop. The dance has only one low-current move. Prusa's firmware runs on its own microcontroller and doesn't pay Klipper's queue-restart cost, so the same order is cheap there.

A shorter load cell settle: no gain

Cutting the seat settle from 150 to 100 ms measured 5.83 s against 5.88 s, which is inside the noise. 150 ms keeps more margin for the reading.

What's left, and why it stays

  • The stop at the trigger line, about 1.5 s. The head has to stand still for the seated reading, because that reading is what lets the park check prove the tool came off. Then the squeeze changes the latch motor's current, which can't be queued, so there is a stop before and after it. Removing this would mean dropping the came-off check, or squeezing at full current, which changes how Bondtech loads the latch.
  • The seat check after the pickup, about 0.75 s. This proves the new tool is on before the heater comes on and printing resumes.
  • Smaller ones. The park check reading and the empty-head reading are short stops, and both are the reason the checks work.

Going further would need firmware-side work: for example, letting the head's microcontroller do the current change on a schedule, or detecting the nozzle with a sensor instead of weighing it, as Prusa does.

Lessons that apply beyond INDX

  • Measure stillness, not just total time. Sampling position and velocity through Moonraker at a few hertz was enough to show that two-thirds of the change was the head standing still.
  • Every M400 or wait_moves() costs about 0.25 s on top of the wait itself. In a macro that runs hundreds of times per print, it is worth asking what each one protects.
  • G4 pauses motion, not the macro. A G4 placed to let a sensor settle doesn't delay the reading unless an M400 follows it.
  • A Python change needs the Klipper service restarted, not just RESTART.
  • Simulation catches mistakes, not stalls. Kalico's batch mode (running klippy.py against a file instead of a printer) confirmed that every variant produced valid commands. It predicted 4.56 → 3.32 s of planned motion, but it doesn't model the queue drains, which were most of the real cost.

Reproducing it

Tested on Kalico at 488b45d5 and BondtechAB/INDX at ae64179, on a Voron Trident 300 with eight docks. The changes are in two local branches, not yet published (full diffs in The code changes):

  • Kalico, branch indx-fast-latch: klippy/extras/indx/heater.py (the WAIT option) and docs/G-Codes.md. Without WAIT=0 the command behaves as before.
  • INDX, branch fast-park: macros/indx-tc-macros.cfg. It needs the Kalico change: an older Kalico ignores WAIT=0 and stops around every latch move as before.

After updating Kalico, restart the Klipper service, not just RESTART, so the new Python code loads.

The timing script, tc-timing.py, is below. It uses only the Python standard library. Run it on the printer host with an output CSV and a list of G-code commands; it sends each command through Moonraker in turn and samples the toolhead while they run:

python3 tc-timing.py run.csv 'CHANGE_TOOL TOOL=1 TEMP=0' M400 'CHANGE_TOOL TOOL=0 TEMP=0' M400

Each command's start and end times are in the #MARK lines at the top of the CSV; a change's time is from the start of its CHANGE_TOOL to the end of the M400 after it. The rows after that are the samples: time, X, Y, Z, head velocity, extruder velocity, nozzle temperature, target and heater power. "Standing still" in this write-up means head velocity under 1 mm/s and extruder velocity under 0.5 mm/s.

#!/usr/bin/env python3
# Run on the printer host. Samples the live toolhead and extruder state through
# Moonraker while a list of G-code commands runs (about 4 samples a second; a
# query takes ~0.25 s), and writes one CSV row per sample after #MARK lines
# giving each command's start and end time.
# Usage (on the printer host): python3 tc-timing.py out.csv 'CMD1' 'CMD2' ...
import json, sys, threading, time, urllib.request, urllib.parse

BASE = "http://localhost:7125"
out, cmds = sys.argv[1], sys.argv[2:]
Q = BASE + "/printer/objects/query?motion_report=live_position,live_velocity,live_extruder_velocity&extruder=temperature,target,power"
rows, marks, stop = [], [], threading.Event()

def sample():
    while not stop.is_set():
        t = time.time()
        try:
            s = json.load(urllib.request.urlopen(Q, timeout=2))["result"]["status"]
            m, e = s["motion_report"], s["extruder"]
            p = m["live_position"]
            rows.append((t, p[0], p[1], p[2], m["live_velocity"], m["live_extruder_velocity"],
                         e["temperature"], e["target"], e.get("power", 0)))
        except Exception as ex:
            rows.append((t, None, None, None, None, None, None, None, str(ex)))
        time.sleep(max(0, 0.025 - (time.time() - t)))

th = threading.Thread(target=sample, daemon=True)
th.start()
for c in cmds:
    t0 = time.time()
    req = urllib.request.Request(BASE + "/printer/gcode/script?" + urllib.parse.urlencode({"script": c}), method="POST")
    try:
        r = urllib.request.urlopen(req, timeout=600).read().decode()[:80]
    except Exception as ex:
        r = "ERROR " + str(ex)
    marks.append((t0, time.time(), c, r))
    print(f"{time.time()-t0:7.2f} s  {c}  -> {r}", flush=True)
    if r.startswith("ERROR"):
        break
time.sleep(0.5)
stop.set(); th.join()
with open(out, "w") as f:
    for m in marks:
        f.write("#MARK,%.3f,%.3f,%s\n" % (m[0], m[1], m[2]))
    for r in rows:
        f.write(",".join("" if v is None else str(v) for v in r) + "\n")
print("samples", len(rows))
